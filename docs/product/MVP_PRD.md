# MVP PRD：走起啦 · Zokila 个人旅行与出行助手

> 状态：名称与方向已确定；首版工作流、具体用户和数据源待验证。本文件描述目标行为，不代表功能已实现。

## 1. 目标

让个人旅行者围绕一次短途自由行，创建并调整一份符合日期、预算、兴趣和出行约束的行程草稿。地点、交通、营业时间和价格等时效信息须显示来源与核查状态。

## 2. 用户与任务

**主要用户假设：** 自己规划数日旅行、希望减少跨平台搜索和行程拼接的人。首轮不按性别限定用户。

**待完成任务：** “我有日期、预算和偏好，想得到一份时间与路线基本可行、容易修改、关键信息能核查的计划。”

## 3. MVP 范围

### 包含

1. 创建行程：输入目的地、日期、人数、预算、兴趣、节奏和必要约束；未确认项可留空。
2. 补全关键条件：Agent 提出少量影响行程可行性的追问，允许用户跳过并记录假设。
3. 生成分日行程草稿：展示活动顺序、估计时间、预算提示、地点信息来源及待核查项。
4. 定向调整：用户修改约束、替换地点或要求重排一天，保留已确认的选择。
5. 审阅与保存：用户能查看输入条件、来源和未解决问题，保存并重新打开行程草稿。

### 不包含

- 自动预订、下单或支付。
- 外卖、穿搭、美妆、礼物等其他消费场景。
- 覆盖所有目的地、实时库存和所有交通方式。
- 社交旅行社区、企业差旅、复杂多人协作和计费。

## 4. 核心流程

1. 用户创建旅行计划并输入已知约束。
2. Agent 提问或明确记录缺失条件。
3. Agent 使用允许的数据源收集地点与出行信息，生成可编辑的分日草稿。
4. 用户检查时间、路线、预算和来源，修改单日或单个地点。
5. 应用保存当前草稿和已确认的约束，便于继续规划。

## 5. 行程草稿结构

1. 日期、目的地、同行人与预算等已确认条件
2. Agent 采用的假设与待补信息
3. 每日活动、地点、预计时间与交通衔接
4. 预算提示与可能超出约束的项目
5. 替代方案、冲突提示与待核查项
6. 地点与出行信息的来源及查询时间

没有可靠信息时显示“待核查”，不要为凑齐行程编造地点或价格。

## 6. 关键交互与行为要求

- 将地点、营业时间、价格和交通信息与对应来源关联展示，并显示查询时间；缺失时明确提示。
- 区分用户确认的条件、来源事实、Agent 建议和待核查内容。
- 约束变更后重排受影响的部分；用户确认过的选择不能被静默替换。
- 提示明显的时间冲突、预算超限或信息过时风险；无法核实时不宣称路线可行。
- 长任务显示阶段和失败原因；失败后保留用户输入与已有草稿。
- 个人信息最小化；外部数据请求和保存方式在接入服务前明确。

## 7. 验收标准

对一份样例短途旅行任务：

- 用户可以输入约束并得到可编辑的分日行程草稿。
- 用户可以替换单个地点或重排一天，已确认的约束保留。
- 时效性事实有来源与查询时间；缺失或冲突时明确标为待核查。
- 用户能识别估计时间、预算假设和未解决问题。
- 生成失败不会静默丢失输入或已有草稿。
- 系统不会自动预订、购买或执行其他外部写操作。

## 8. 首轮评估

选取 3–5 个真实或脱敏的短途行程，比较手工规划与 Agent 辅助流程。记录完成时间、用户修改点、过时信息、路线冲突和复用意愿。小样本用于发现问题，不据此宣称普遍效果。

## 9. 当前未决项

- 首个目标用户与行程类型是什么？
- 哪些地点、地图、交通和价格数据源能稳定、合法地接入？
- 首版只做规划，还是提供跳转到预订平台的链接？
- 行程保存、导出和分享方式，以及个人数据的保留期限是什么？
- Pi SDK 的具体工具接口与运行方式在接入前核实。
