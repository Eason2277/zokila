# AI 协作开发约定

本文用于让人和 AI 在本项目中保持共同目标。产品仍处于探索阶段；不确定的产品假设必须显式说明，不能在实现中悄悄变成已确认需求。

## 文档职责与读取顺序

1. 当前用户要求和 `AGENTS.md` 是工作指令；`AGENTS.md` 主要记录稳定工程规则。
2. `PRODUCT_CONTEXT.md` 是现行产品方向与产品不变量的简明入口。
3. `docs/product/PRODUCT_BRIEF.md` 记录用户、问题、价值与待验证假设；`docs/product/MVP_PRD.md` 记录首版目标行为和验收标准。
4. `docs/decisions/` 记录历史决定与取代关系；不要把已被取代的决定当作现行要求。
5. `docs/AGENT_HANDOFF.md` 是有日期的工程状态快照，使用前核对当前代码和 Git 状态。

同一问题出现冲突时，先区分新旧与事实/假设；当前用户明确要求优先，现行产品文档优于旧决策。不要以手册文字代替对代码运行状态的核查。

## 每个任务开始前

- 阅读与本次任务直接相关的产品文档和代码，不要无差别加载整个仓库。
- 用简短文字复述目标、范围、验收标准和关键假设。
- 若问题可通过可逆的小实现解决，先推进；若缺少信息会导致数据泄露、对外承诺或大范围返工，先提出一个聚焦问题。
- 保留用户已有的未提交更改，不覆盖、不清理无关文件。

## 实现约定

- 一次只完成一个可审查的小切片；避免顺手扩展范围。
- 先说明将修改哪些文件和用户可见行为，再实现。
- 不添加未经需求支持的工具、数据采集、外部写操作或自动发送能力。
- 任何模型输出都视为不可信输入；来源、权限和用户确认边界需要在设计中明确。
- 地点、日期、同行人与个人偏好按敏感个人上下文处理；密钥不得写入源码、日志或文档样例。
- 旅行信息中的价格、营业时间、交通班次与可订状态必须保留来源和查询时间；不能用流畅文案掩盖证据缺失。
- 新的产品/技术决定写入对应文档，附日期、背景、决定、影响和仍待验证项。

## 完成任务时

- 汇报改动、原因、验证结果和未解决问题。
- 仅运行与任务相关且项目已有的验证命令；没有运行就明确说明。
- 若实现与产品假设冲突，指出冲突并更新提议，不要自行把假设改写成事实。
- 对较大的任务先给出简短实施计划；对小任务直接完成。

## 当前状态入口

现行产品方向见 `PRODUCT_CONTEXT.md`；首版范围见 `docs/product/MVP_PRD.md`；代码与验证状态见有日期的 `docs/AGENT_HANDOFF.md`，并以当前工作树为准。此处不复制易过时的状态清单。
