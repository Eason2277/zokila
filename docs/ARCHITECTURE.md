# Zokila 架构现状与目标

> 更新：2026-11-15。本文件区分已实现、目标设计和待验证项；代码与当次运行结果优先于本文的状态快照。

## 目标与当前结论

Zokila 是面向普通旅行者的个人旅行与出行助手，使用 Pi 作为 Agent 底座。用户已确定未来同时提供 **CLI 模式和图形客户端模式**。当前仓库保留完整 Pi monorepo，并在 `apps/market-research-workbench/` 放有 Electron + React/TypeScript 原型。**现有权限边界可以作为桌面原型的起点；CLI、旅行产品流程和两端共享能力都尚未实现，不能供真实旅行用户使用。**

## 双端目标架构（目标，部署方式待验证）

```text
Zokila CLI ─────┐
                ├── Zokila application services ── Pi Agent runtime ── travel data/tools
Zokila Client ──┘                 │
                                  └── trip state, preferences, permissions, provenance
```

Pi 上游已有通用 Pi CLI；它是 Agent 开发/运行工具，不等于 Zokila 的旅行产品 CLI。Zokila 的 CLI 是产品自己的命令入口，应提供旅行任务语义（例如创建行程、调整计划、查看来源），底层通过 Pi SDK/Agent runtime 复用 Pi 能力。图形客户端与 Zokila CLI 是同一产品的两种交互入口，应复用旅行领域操作、行程状态、来源信息和操作确认规则，不各自实现一套 Agent 逻辑。

本地优先有利于本地运行，但跨设备同步和模型凭证管理更复杂；服务端优先便于多端共享，但增加账号、留存和运维责任；混合方式需要解决本地与云端同步。先验证用户是否需要两种入口及跨设备连续性，再确定部署方式。无论采用哪种方式，CLI 也必须遵守相同的敏感数据处理和外部操作确认规则。

## 已实现的边界

| 层 | 当前状态 |
| --- | --- |
| Pi 源码 | 保留上游 monorepo，可继续读取 SDK 并获取上游更新；Zokila 尚未调用 SDK。 |
| Electron 主进程 | 创建桌面窗口、加载受限的本地页面、处理有限的窗口控制 IPC。 |
| preload | 只向 React 暴露窗口控制；没有暴露原始 IPC、文件系统或 Shell。 |
| React 渲染进程 | 展示旧市场研究演示数据；表单和提示消息只更新本地 UI 状态。 |
| 旅行数据与服务 | 未实现行程模型、地点与交通数据接入、保存、用户账号、Pi 会话、结果评测和发布包。 |
| CLI / 客户端 | 只有旧 Electron 客户端原型；Zokila CLI 和两端共用的旅行服务都未实现。 |

旧静态页面 `workbench.html`、`app.js` 是历史原型；当前入口是 `index.html` → `src/main.tsx` → `src/App.tsx`。不要把表单提交成功或浏览器预览当作 Agent 已完成任务。

## 最小可用闭环（目标，尚未实现）

1. 用户输入目的地、日期、预算、兴趣与约束；系统保存可修改的行程草稿。
2. Agent 通过受限工具获取可用的地点及出行信息，保留来源、查询时间和不确定性。
3. 系统生成分日行程，检查明显的时间、路线和预算冲突；用户可以局部修改。
4. 中断或工具失败时保留已确认的输入与草稿，并明确告知用户失败原因。
5. 用户对任何预订、购买或外部发送操作作最终确认；首版不执行这些动作。

先选一个明确的旅行场景和可合法使用的数据源，跑通上述闭环，再扩大目的地、场景和自动化范围。业务结构应由应用层拥有；Pi 负责 Agent 运行和工具调用，不代替用户数据、权限、任务状态和审计逻辑。

## 应用形态与部署待决

Electron 主进程承载 Pi SDK 适合验证本地桌面原型，但普通旅行者是否愿意安装桌面程序尚未验证。若转向 Web 或移动端，Pi 会话及模型凭证应留在受控服务端，客户端只访问明确的业务 API。不能把模型密钥或通用 Pi 工具暴露给浏览器/移动客户端。选择应用形态之前，先验证用户场景、设备使用方式和数据源。

## 发布前的主要缺口

- 当前 UI 仍是制造业市场研究；没有旅行任务的真实交互。
- 没有 Pi SDK 接入、模型配置和受限旅行工具。
- 没有持久化、个人数据处理方案、数据源授权或结果质量验证。
- Electron 原生启动及打包未在本次审查中验证；以当次实际运行结果为准。
- 仓库继承 Pi 上游的 GitHub Actions，其中有发布和写入流程。作为个人产品仓库时，应单独审查并控制这些工作流；不能把上游 CI 成功当作 Zokila 产品验收。
